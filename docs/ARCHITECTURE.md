# SideQuest — Architecture (local developer guide)

> Local-only document. Nothing here is pushed to the public GitHub repo, which
> intentionally ships no code or technical docs. For a file-by-file map of the
> whole repository, see `docs/CODE-TREE.md`.

## What this is

SideQuest is a South-African scavenger-hunt game: a quest map, a shuffled
quest feed, multi-stop chains, seasonal & live events, a stats dashboard with
levels/ranks/badges, and a social layer (friends, squads, community quests).
It runs in any browser and as a Capacitor Android app. All game data is static
and free; Supabase adds identity, syncing, and community features
progressively.

## Stack

| Layer | Choice |
|---|---|
| Language / UI | TypeScript + React 19 |

| Routing | react-router (hash-free BrowserRouter) |

## Key flows

### Startup
`main.tsx` mounts `GameProvider` (loads localStorage state) → `App.tsx` ensures
an anonymous Supabase identity (creating one on first launch), pushes the
local state up (idempotent), registers FCM push on Android, subscribes to
friend-request & squad events, kicks off `syncRemoteEvents()`, and renders the
router (with the `UpdatedNotice`/`UpdateBanner` version checks). The bottom
nav links Home / Map / Feed / Build / Friends / Profile.

### Completing a quest
A quest sheet (`QuestSheet`) starts an active session; finishing it calls
`completeActiveSession` in `store.tsx`, which awards XP (with streak/weather
bonuses) and records the completion + memory. The new state is then pushed to
Supabase by `App.tsx` via `sync.ts` when online: an idempotent push at launch,
plus a debounced (1.5s) push whenever XP/streak/completions change. Levels,
ranks, and badges are all derived pure functions in `game.ts`, so the UI just
re-renders.

### Live events (no scheduled jobs)
Events come from two sources merged in `eventsSync.ts`:
1. A static snapshot (`public/events-remote.json`) — regenerated by hand with
   `npm run fetch:events` (`scripts/fetch-events.mjs`) and committed to the
   download repo; cached 12h per device.
2. The Ticketmaster Discovery API, queried **from the browser at launch**
   (Ticketmaster enables CORS for this API). Active only when
   `VITE_TICKETMASTER_API_KEY` is set; cached 1h.

Live rows win on a `title|city` tie; both are filtered to upcoming events
(`isUpcomingEvent`, ~6-month horizon) and deduped against the bundled quests.
Any failure falls back to cache, then to nothing — the bundled quests are
always the floor.

### Sync & identity
On first launch the app signs in **anonymously** (Supabase anonymous auth) —
the device keeps that uid forever, and the profile row is `id = auth.uid()`.
RLS policies make each user read/write only their own row. Accounts (email)
are optional upgrades; usernames are user-typed, never generated.

## Data model (local)

`sidequest-state-v1` in localStorage holds the whole game:
playerName, homeBaseId, xp, streak, completions map (id → {at, xp, weather,
distance}), memories, activeSession, friends, custom chains/quests. Supabase
mirrors profiles, completions, chains, friends, squads, community quests,
reviews, and push tokens (see `sync.ts` for the table/column names used). The
race/challenge feature was fully removed in migration 0009 — its tables,
triggers, and push functions no longer exist in the live schema.

## Testing

- `npm test` — 61 Vitest tests: `game.test.ts` (levels, ranks, badges, stats,
  formatting) and `eventsSync.test.ts` (live-event transform + source merge).
- `npm run check:quests` — data-integrity checks over the quest catalogs.
- No component or E2E tests yet.

## Known nits (do not "fix" casually)

- The race/challenge feature was removed in migration 0009 (v1.0.15). Its
  table, triggers, and `push_challenge*` push functions are gone from the live
  schema; migrations 0003/0006/0007 still contain the historical SQL — don't
  build on it.

- `anywhere()` in `quests.ts` does not set `anywhere: true` (unlike `qAny` in
  `social.ts`) — see the NOTE comment at the builder. Changing it pulls those
  quests off the map; decide the intended UX first.
- The SA city atlas used for event placement is duplicated in
  `eventsSync.ts` (client) and `scripts/fetch-events.mjs` (build script) —
  keep them in sync.
- `styles.css` is one 1.7k-line file; component-scoped classes live there by
  convention, not in component files.
- The download repo on GitHub is intentionally code-free: the app's events
  snapshot lives there as a static file, refreshed manually.

## What a new developer should read first

In order:

1. `README.md` — what the product is, for context.
2. This file — where everything lives and how the flows connect.
3. `src/main.tsx` + `src/App.tsx` — how the app boots and composes.
4. `src/lib/store.tsx` — the persisted game state and every mutation.
5. `src/lib/game.ts` + `src/lib/game.test.ts` — the pure rules (levels, ranks,
   badges) with their tests right beside them.
6. `src/data/quests.ts` — the quest data model and the builder helpers.
7. `src/lib/sync.ts` — how the local state meets Supabase.
8. `src/lib/eventsSync.ts` — the events pipeline (snapshot + live Ticketmaster).
9. One screen end-to-end: `src/components/Generator.tsx` (feed) → `QuestSheet`
   → `store.tsx` `completeActiveSession`.

Then run `npm install`, `npm run dev`, and `npm test` to get moving.
